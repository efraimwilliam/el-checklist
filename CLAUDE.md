# Sistem Checklist Kerjaan eL Hotel & Resort Sanur

Laravel 13 + Blade + Tailwind 4 (Vite), MySQL, Pest. Timezone Asia/Makassar (WITA). UI berbahasa Indonesia.

- `public/build` ikut di Git (server tanpa Node.js): jalankan `npm run build` sebelum commit bila CSS/view berubah.
- Test: `php artisan test` (database MySQL `checklist_test`). API absensi selalu dipalsukan (`Http::preventStrayRequests`,
  helper `fakeAttendance()` / `attendanceAccepts()` / `attendanceRefuses()` / `loggedIn()` / `nextRequest()` di `tests/Pest.php`).

## Login (Sistem Absensi)
- Satu kolom login: pegawai memakai username + PIN absensi; HOD / HR / Administrator (akun dashboard absensi) boleh memakai password dashboard absensi di kolom yang sama. Server ini meneruskan ke API absensi (`config/attendance.php`, `.env` `ATTENDANCE_API_*`;
  token = `TASKS_API_TOKEN` di Sistem Absensi; endpoint `POST /api/v1/tasks/auth/verify-password` dicoba dulu, lalu `POST /api/v1/tasks/auth/verify-pin`). Browser tidak pernah memanggil API absensi.
- Portal SSO (opsional; `App\Support\PortalClient`, `Auth\SsoController`, middleware `VerifySsoSession`, route `/sso/login`, `/sso/callback`, `/sso/logout`): aktif bila `SSO_PORTAL_URL`, `SSO_CLIENT_ID`, `SSO_CLIENT_SECRET` terisi
  (`config/services.php` -> `sso`; `SSO_ENABLED=false` = mati darurat). Mode login dibaca dari Portal (`/api/sso-mode`: `required` = `/login` langsung ke Portal & username+PIN ditolak, `both`, `local`).
  Alur OAuth2 authorization code; server menukar kode lalu `GET /api/user`. Akun lokal dicocokkan lewat username Portal = `employees.username`, dikunci di `users.sso_user_id`; harus `canUseApp()`; peran/departemen tetap di `/admin/akses`.
  `VerifySsoSession` (grup route `auth`): lapor aktivitas ke Portal tiap menit (`/api/aktivitas`, 401 = sesi diakhiri), cek `/api/user` tiap `SSO_CHECK_MINUTES` menit; Portal mati tidak mengeluarkan siapa pun; JSON -> 401. Keluar dari sesi Portal = redirect ke `{portal}/keluar`.
  Login username + PIN ke API Absensi tetap jalan di mode `both`/`local`. Log: `login.sso_success`, `login.no_access`.
  Akun sistem Portal (`SSO_SYSTEM_ACCOUNTS`, mis. `admin`; ditolak Absensi di endpoint login dan sync karena `is_system_account`) masuk lewat SSO saja: `SsoController::systemUser` membuat `employees` tanpa `external_id` (kolom nullable) dan `users` Administrator. Sinkron Absensi tidak menonaktifkan baris tanpa `external_id`.
- Profil (`/profil`, `AccountController`; HR/Administrator juga lewat "Ubah akun Sistem Absensi" di Atur tugas pegawai, gate `manage-tasks`): ubah username dan password dashboard. Disimpan di Absensi lewat `PATCH /api/v1/tasks/account` (`AttendanceApiService::updateAccount`); PIN atau password pengubah ikut dikirim untuk diperiksa di sana, tidak disimpan di sini. Salinan `employees.username` ikut diperbarui. Password baru hanya untuk peran HOD/HR/Administrator (`Role::usesDashboardPassword`). Aturan Absensi berlaku: diri sendiri = jeda 30 hari & password lama wajib; orang lain = `canManage`, password baru jadi sementara. PIN tidak diubah dari sini.
- Tidak ada password/PIN pegawai di database ini, di sesi, maupun di log. `users` tanpa kolom password untuk pegawai; tanpa "ingat saya".
  Pengecualian: akun sistem (tanpa data pegawai di absensi, mis. `admin`) boleh punya `users.password` (hash bcrypt) yang dibuat lewat `checklist:admin-lokal`
  (password diminta di terminal). Login-nya di form yang sama, hanya saat mode Portal bukan `required`; tidak pernah ke Absensi; kolom password diabaikan `AuditObserver`.
- Akun Staff uji lokal: `php artisan checklist:staff-lokal {username} --departemen=Engineering [--pin=]` (`CreateLocalStaff`; HANYA saat `APP_ENV=local`, menolak username pegawai Absensi). Membuat pegawai tanpa `external_id` + pengguna Staff dengan PIN/password sendiri (hash) lewat jalur `passwordAccount` yang sama dengan akun sistem; jabatan checklist diisi dari jabatan pertama departemen yang punya tugas. Tanpa `--pin`, PIN 6 digit acak ditulis ke `storage/app/private/akun-uji/{username}.txt` (di luar Git, tidak ditampilkan di terminal).
- `App\Attendance\AttendanceApiService` menormalkan respons ke `AuthOutcome` (alasan dari API + `timeout`/`unavailable`/`malformed`/`not_configured`); login tidak diulang otomatis.
- `Auth\AttendanceLoginController`: kunci 5 gagal / 15 menit per username+IP (gangguan API tidak dihitung) + throttle `login` 20/menit per IP;
  pesan umum untuk salah PIN/password & nonaktif; `password_must_change` = minta ganti password sementara di Absensi dulu; `pin_not_set` = pesan petunjuk saja (minta HR/HOD membuka izin buat PIN, lalu buat PIN di aplikasi absensi dan kembali ke sini); tidak ada tombol/pengalihan, PIN tidak pernah dibuat di aplikasi ini.
  Berhasil = pegawai lokal dicocokkan lewat `external_id` (id absensi), harus punya `users` aktif, sesi diregenerasi, `auth.logged_in_at` disimpan.
- `EnsureActiveSession` (semua route login): keluar otomatis bila akun dicabut, pegawai nonaktif di absensi, atau melewati `session.absolute_lifetime`
  (default 720 menit). Batas diam = `SESSION_LIFETIME` (360 menit = 6 jam, sesuai tutorial). Logout = invalidate + token CSRF baru. Log hasil login: channel `auth` (`storage/logs/auth-*.log`).
- `ATTENDANCE_API_VERIFY_TLS=false` ditolak saat boot di produksi.

## Data master
- `attendance:sync` (tiap jam, juga tombol "Sinkron dari absensi" di Akses pengguna): `EmployeeSyncService` mencocokkan departemen lewat id absensi → kode → nama,
  pegawai lewat id absensi; pegawai tidak pernah dihapus, yang hilang dari absensi dinonaktifkan.
- `checklist:import-workbook {xlsx}` (`WorkbookImporter`): sheet Departemen, Jabatan, Tugas dari workbook checklist lama; bisa diulang; sheet Akun (PIN) TIDAK dibaca.
  Departemen yang sudah tersinkron tetap memakai nama absensi.
- Akses pertama: `php artisan checklist:grant {username} admin` (setelah sync).

## Kolom tanggal (satu sistem di seluruh aplikasi)
- Komponen kalender bergaya emas di `resources/js/date-picker.js`: `data-date-field` (satu tanggal, Isi checklist; `data-submit` = kirim form saat dipilih) dan `data-range-field` (rentang, Riwayat & Dashboard: klik tanggal mulai lalu selesai, form langsung dikirim). Tombol `data-*-trigger` menampilkan tanggal, panel `data-*-panel`; pilih bulan dan tahun lewat nama bulan. Tanpa tombol Tampilkan.
- Rentang di server: `App\Support\DateRange::fromRequest` (`from`/`to`, dibalik bila terbalik, maksimal 92 hari, tidak ke depan).

## Laporan (`/laporan`, menu Laporan; `ReportController`, `App\Reports\ReportService`)
- Rentang tanggal (kalender emas, `from`/`to`) memakai `DashboardService` + isi laporan: KPI (skor, kelengkapan, staff tanpa checklist, backlog review = lengkap belum direview > 2 hari), tabel per departemen (checklist, lengkap %, pending, belum direview, staff yang belum punya checklist), tugas sering tertunda, alasan Pending terbaru.
- Catatan tindak lanjut (`report_notes`): siapa pun yang boleh melihat laporan menambah catatan untuk rentang itu (HOD wajib pilih departemennya; HR/GM/Admin boleh "Semua departemen"); catatan dihapus oleh penulisnya, atau HR/Administrator. Catatan tampil bila rentangnya beririsan dengan laporan.
- Cetak: tombol Cetak (`window.print`); kontrol disembunyikan saat cetak.
- Isi tambahan: pembanding periode sebelumnya (`previous`), skor per jabatan dan 10 staff terendah, tugas sering dilewati (Pending/kosong minimal 2×), kebiasaan pengisian (diisi hari yang sama, rata-rata hari sampai direview), foto wajib yang kurang, pola Pending per hari (Senin–Minggu).
- Bawaan rentang Laporan: hari ini. Staff yang libur/cuti/tanpa jadwal di Absensi tidak dihitung "belum punya checklist" (jadwal per hari dari `AttendanceApiService::schedules`; bila Absensi tidak terbaca, semua yang belum punya checklist dihitung dan halaman menyebutnya).
- Riwayat juga punya "Unduh Excel" (`/checklists/ekspor.xlsx`, filter sama dengan halaman). Penulis Excel bersama: `App\Reports\ExcelReport`.
- Ekspor Excel: `/laporan/ekspor.xlsx?from=&to=` (route `laporan.export`; file .xlsx dengan lembar Ringkasan dan Checklist, PhpSpreadsheet).
- Tab Laporan (partial `laporan/partials/head`; semua gate `view-checklists`, departemen mengikuti `accessibleDepartmentIds`, rentang tanggal sama maks 92 hari kecuali Bulanan):
  - **Ringkasan** (`/laporan`): isi di atas.
  - **Masalah & Pending** (`/laporan/masalah`, `App\Reports\IssueService`): peringkat tugas bermasalah lintas staff/hari (bermasalah = Pending + Ongoing + kosong; tugas dikenali dari departemen + judul; jabatan yang mengerjakan digabung dalam satu baris), Pending berulang (>= 3 hari berturut-turut atau >= 4 kali per staff + tugas), peta panas departemen x hari, alasan Pending dengan pencarian. Detail satu tugas `/laporan/masalah/tugas`: tren harian, staff, kejadian.
  - **Masalah terbuka** (bagian di tab yang sama, `IssueService::open`): tiap isian Pending tertua dulu dengan umur (hari) dan tindak lanjut (`issue_followups`, satu baris per isian: Terbuka / Ditangani / Selesai + catatan, model `IssueFollowup`, tercatat di log). Diisi lewat `POST /laporan/tindak-lanjut/{item}` (`ReportController::followUp`) oleh HOD departemennya / HR / Administrator; GM hanya melihat. Pending yang tugas sama milik staff sama berstatus Done pada tanggal sesudahnya = "Selesai otomatis" (dihitung saat dibaca, tidak disimpan); disembunyikan kecuali "Tampilkan yang selesai".
  - **Parameter** (`/laporan/parameter`, `ParameterReport`): per parameter angka / stand meter (jumlah data, min, rata-rata, maks, di luar batas min/maks, konsumsi meter = nilai terakhir - pertama dalam rentang) dan daftar pembacaan di luar batas atau pilihan bukan nilai normal. Nilai dibaca dari teks (koma desimal diterima).
  - **Bulanan** (`/laporan/bulanan`, `MonthlyReport`): 12 bulan terakhir dari `report_snapshots` (ringkasan harian per departemen x jabatan, `SnapshotService`). Diisi `php artisan laporan:snapshot` (tiap malam 03:50, menghitung ulang 7 hari terakhir; opsi `--dari`, `--sampai`, `--backfill` sekali untuk data lama), jadi angka bulanan tetap ada walau checklist dihapus.
  - **Data** (`/laporan/data`, `DataExplorer`): satu baris = satu isian tugas; filter departemen / jabatan / staff / status / ada catatan / kata kunci; 50 per halaman; nilai parameter dan jumlah foto; unduh `/laporan/data/ekspor.xlsx` (maks 50.000 baris, `ExcelReport::itemSheet`).
- Log aplikasi lebih tua dari `AUDIT_RETENTION_DAYS` (bawaan 180, `config/audit.php`) dihapus tiap malam 03.40 (`audit:prune`).
- `php artisan laporan:mingguan`: ringkasan 7 hari sampai kemarin ke `storage/app/private/laporan/`, dijadwalkan Senin 07:00 WITA. Belum dikirim email (menunggu alamat GM).

## Kendala (di kamar atau lokasi lain) dan Peta kamar
- Alur: tamu melapor ke Front Office (atau staf menemukan sendiri) -> dicatat di menu **Kendala** (dulu "Kendala kamar"; URL dan nama route tetap `/kamar/kendala`, `kamar.*`) (`/kamar/kendala`, `RoomIssueController`, gate `room-issues` = semua pengguna berakses termasuk Staff) -> diteruskan ke departemen / jabatan / pegawai yang menangani (dipilih saat mencatat) -> departemen itu mencatat pekerjaan yang sudah dilakukan di kamar -> ditandai selesai. Peta kamar di Laporan memakai data ini.
- **Lokasi dan tujuan** (migrasi 2026_11_22): `room_issues.room_id` boleh kosong; lokasi = kamar (`room_id`, dipilih) ATAU tempat lain (`location`, teks bebas maks 120 dengan saran `RoomIssue::SUGGESTED_LOCATIONS` + yang pernah dipakai; dicocokkan tanpa membedakan huruf besar / kecil). Tepat salah satu (divalidasi di `store`, `place_type` room|location; tanpa `place_type` dianggap room bila ada `room_id`). Kendala serupa, berulang, dan track record memakai lokasi yang sama (`RoomIssue::scopeAtPlace`, `isAtPlace`); track record lokasi lain di `/kamar/lokasi?nama=` (`kamar.place`, view `rooms.show` yang sama). Judul: `placeTitle()` ("Kamar 305" / nama lokasi). Peta kamar dan kartu denah hanya menghitung kendala di kamar (`RoomReport` `whereNotNull(room_id)`). "Diteruskan ke" (`target_type` department|position|employee; bawaan department): `assigned_department_id` SELALU terisi (departemen pilihan / bawaan kategori, atau departemen jabatan / pegawai), ditambah `assigned_position_id` (jabatan; yang bisa mengambil = pegawai dengan `checklist_position_id` itu) atau `assigned_employee_id` (hanya pegawai itu; wajib punya akun aktif). `RoomIssue::isForUser` / `scopeForUser`: tujuan departemen saja = semua anggota departemen; jabatan / pegawai = yang dituju saja; HOD memegang semua tujuan di departemen yang dipegangnya. Dipakai policy, daftar (`visibleTo`), penanda menu (`User::newRoomIssueCount`), dan sorotan "Untuk Anda / jabatan Anda / departemen Anda". `targetLabel()` = "Departemen" / "Jabatan · Departemen" / "Pegawai · Departemen".
- Tabel: `rooms` (nomor unik, lantai, gedung, tipe), `issue_categories` (nama + departemen penanggung jawab bawaan; bawaan: AC, Listrik & lampu, Air & sanitasi, Perabot, TV & elektronik -> Engineering; Kebersihan & linen, Minibar & amenities -> Housekeeping; Lainnya; dicocokkan lewat nama departemen saat migrasi), `room_issues` (kamar, kategori, sumber tamu/staff/inspeksi, prioritas biasa/mendesak, `assigned_department_id`, status baru/dikerjakan/selesai), `room_issue_updates` (catatan pekerjaan, jejak teruskan/selesai). Semua tercatat di log aplikasi (`AuditObserver`).
- `RoomIssuePolicy` (selalu di server): lihat = Admin/HR/GM semua, lainnya yang dilaporkan sendiri atau yang diteruskan kepadanya (`RoomIssue::isForUser` / `visibleTo`; `User::issueDepartmentIds()` = departemen sendiri + departemen HOD); `claim` (Saya ambil) = yang kendalanya diteruskan kepadanya (`isForUser`), HR, Administrator, bukan GM, selama belum diambil dan belum selesai; `work` (isi status Done / Ongoing / Pending) = hanya setelah diambil, oleh yang mengambil, HOD departemen penanggung jawab, HR, Administrator, dan hanya sebelum Done; `reopen` = HR / Administrator. Status kendala: baru -> Ongoing (`dikerjakan`) -> Pending (`tertunda`, wajib beralasan) -> Done (`selesai`); setelah diambil, formulir hanya berisi pilihan Done / Ongoing / Pending, catatan pekerjaan, dan Simpan (`RoomIssueController::progress`, route `kamar.issues.update`); Done mengunci kendala.
- Data kamar dan kategori: `/admin/kamar` (`Admin\RoomController`, gate `manage-tasks`, menu Tugas > Data kamar): kartu ringkasan (kamar, aktif, lantai), dua tab (Kamar | Kategori kendala), daftar rapi per baris dengan penyaring cari / lantai / status, tambah dan ubah lewat dialog (`_form` + `_id` membuka kembali dialog yang sama saat gagal simpan). Impor Excel `/admin/kamar/impor` (`App\Rooms\RoomImport`, dua langkah periksa lalu simpan; kolom: Nomor kamar wajib, Lantai, Gedung, Tipe; nama kolom alternatif dikenali; lantai kosong ditebak dari nomor 305 -> 3; contoh berkas di `/admin/kamar/contoh.xlsx`).
- **Peta kamar** (`/laporan/kamar`, menu Laporan, bukan Staff; `App\Reports\RoomReport`): peta per lantai (warna menurut jumlah kendala), kamar langganan masalah (>= `RoomReport::REPEAT_THRESHOLD` = 3 kendala dalam rentang), per kategori, per departemen penanggung jawab, rata-rata jam dari dicatat sampai selesai; filter departemen dan kategori; rentang berdasarkan tanggal dicatat (bawaan 30 hari). Riwayat satu kamar: `/laporan/kamar/{room}`.
- **Denah (peta sungguhan)**: tab "Denah" di Data kamar (`/admin/kamar?tab=denah`, `Admin\FloorPlanController`, gate `manage-tasks`). Unggah PDF / PNG / JPG: PDF dibaca dan diubah menjadi gambar DI BROWSER (`resources/js/floor-plan-upload.js`, `pdfjs-dist` dimuat malas, pilih halaman, sisi terpanjang 2400 px) dan hanya gambar yang dikirim; server memeriksa dan menyimpan PNG privat maks 3000 px (`App\Rooms\FloorPlanImage`, `floor-plans/{uuid}.png`, dilayani `GET /denah/{plan}/gambar` untuk pengguna kendala kamar). Tabel `floor_plans` (nama, lantai, gambar, ukuran, urutan, aktif) dan `floor_plan_areas` (satu baris per kamar, `room_id` UNIK = satu kamar hanya satu kotak di satu denah; `x,y,w,h` dalam persen 0-100 dari gambar). Editor `/admin/denah/{plan}` (`resources/js/floor-plan-editor.js`, tanpa library): pilih kamar lalu seret di atas gambar untuk menggambar kotak; kotak bisa digeser, diubah ukuran lewat 8 pegangan, Delete menghapus, panah menggeser halus, zoom Pas / + / -; Simpan = satu `PUT /admin/denah/{plan}/area` berisi seluruh daftar (divalidasi: kamar ada dan aktif, batas 0-100, w/h minimal 0.5, tidak ganda, tidak dipakai denah lain; kotak yang melewati tepi dipotong). Menghapus denah menghapus kotaknya dan gambarnya (kamar dan kendala tidak berubah).
- Kotak GEDUNG / AREA (peta kawasan): selain kamar, satu kotak bisa mewakili satu gedung / area (`floor_plan_areas.building`, `room_id` kosong; unik per denah, nama yang sama boleh di denah lain, mis. peta kawasan dan zonanya). Nilainya = kolom `rooms.building` ("Gedung"); warna dan hitungan dijumlahkan dari kendala SEMUA kamar dengan gedung itu (`RoomReport` `buildings` + `buildingMax`), klik membuka `/laporan/kamar/gedung?nama=` (`ReportController::building`, daftar kamar dan kendalanya). Editor punya dua tab (Kamar | Gedung / area) dan kotak nama gedung baru. Mengisi gedung banyak kamar sekaligus: Data kamar > Kamar, saring (cari / lantai / status), lalu "Atur gedung untuk N kamar yang cocok" (`RoomController::setBuilding`, berlaku untuk SEMUA yang cocok, bukan hanya halaman tampil; wajib ada penyaring). Satu kotak harus kamar ATAU gedung (divalidasi di `saveAreas`).
- Peta kamar tampilan Denah: `/laporan/kamar` memakai denah bila ada denah aktif yang punya kotak (bawaan; `?tampilan=daftar` = kotak per lantai seperti semula; `?denah=ID` memilih denah); tiap kotak kamar berwarna menurut jumlah kendala (skala sama dengan Daftar), label nomor + jumlah, klik ke riwayat kamar (`laporan.room`), zoom (`floor-plan-map.js`), dan daftar "Belum ada di denah" untuk kamar bermasalah yang belum ditandai. `RoomReport::build` mengembalikan `rooms` (data per kamar berkunci id).
- Kendala serupa (aturan: satu kamar + satu kategori + belum selesai = satu kendala): dialog Catat kendala memeriksa lewat `GET /kamar/kendala/serupa` (`RoomIssueController::duplicate`, `RoomIssue::openDuplicate`) dan menawarkan "Tambahkan laporan ke kendala itu" (bawaan; `merge_into`, masuk riwayat sebagai `kind` laporan, prioritas naik bila mendesak) atau "Buat kendala baru" (`force_new`). Server menolak membuat kendala ganda bila belum memilih. Yang menambahkan laporan ikut bisa melihat kendalanya (`RoomIssue::visibleTo` / policy `view` juga memeriksa `room_issue_updates.user_id`).
- Berulang (`room_issues.recurrence`, `RoomIssue::nextRecurrence`): 1 + jumlah kendala kategori sama di kamar sama dalam `RECURRENCE_DAYS` = 30 hari terakhir; badge "Berulang ke-N" di daftar, detail, riwayat kamar, dan kartu "Kendala berulang" di Peta kamar. Halaman detail punya "Track record kamar N" (dilihat SEBELUM mengambil), dipisah supaya tidak tercampur: (1) kendala sejenis = kategori sama di kamar itu, departemen mana pun, lengkap dengan pekerjaan yang dicatat (Ongoing / Pending / Done); (2) pekerjaan departemen pengguna di kategori lain (dilipat); (3) kendala departemen lain (dilipat). Untuk pegawai yang sudah mengambil kendala itu, diganti satu kartu dilipat "Track record kamar N (jumlah)" yang hanya memuat kendala di kamar itu yang ditangani departemen kendala ini (mis. Engineering), dengan tautan ke halaman kamar tersaring departemen. Track record penuh satu kamar: `/kamar/{room}` (`RoomIssueController::room`, terbuka untuk semua pengguna kendala kamar, filter kategori dan departemen, partial `rooms/partials/record-item`). Kendala baru yang berulang menambah catatan sistem `kind` berulang di kendala lama ("Muncul lagi sebagai kendala #N", `room_issue_updates.related_issue_id`) dengan tautan.
- "Cetak riwayat" satu kendala (`GET /kamar/kendala/{issue}/kronologi`, `RoomIssueController::chronology`, tombol "Cetak riwayat" di halaman detail; BUKAN Chronology Report tamu; policy `view`): halaman siap cetak / simpan PDF (`window.print`, header aplikasi disembunyikan saat cetak): ringkasan (kamar, kategori, status, sumber, departemen, pengambil), waktu respons (dicatat -> diambil), waktu penanganan (diambil -> Done), total, lalu urutan waktu dari "Kendala dicatat" sampai Done (diambil, Ongoing, Pending, Laporan tambahan, Muncul lagi, Pengambilan dilepas) dengan selang waktu antar kejadian, pelaku, departemen, dan foto, serta kolom tanda tangan.
- Foto bukti pekerjaan: formulir Status pekerjaan punya tiga tombol sejajar Kamera (`<input capture=environment>`, kamera bawaan HP), Galeri, dan Catatan (membuka kolom catatan; otomatis terbuka saat Pending), maksimal 3 foto per simpan, dikecilkan di perangkat (1280 px) lalu diolah ulang di server (`App\Support\PhotoReencoder`, dipakai juga foto checklist: putar EXIF, maks `checklist.photos.max_edge`, JPEG baru tanpa metadata). Tabel `room_issue_photos` (menempel pada `room_issue_updates`), berkas privat `room-issue-photos/{kendala}/{uuid}.jpg` (`RoomIssuePhotoService`), dilayani `GET /kamar/kendala/{issue}/foto/{photo}` untuk semua pengguna kendala kamar (track record kamar terbuka untuk mereka). Foto tampil di Riwayat kendala dan track record; `checklist:prune-photos` ikut menghapus foto kendala yang lewat masa simpan.
- Penanda: menu header "Kendala" menampilkan angka kendala berstatus baru yang diteruskan kepada pengguna (departemennya, jabatannya, atau dirinya; `scopeForUser`) (`User::newRoomIssueCount()`, satu query per permintaan); halaman daftar menyorot yang baru untuk departemen itu dan punya kartu "N kendala baru menunggu departemen Anda". Admin / HR / GM tanpa departemen tidak mendapat angka (hanya departemen sendiri atau yang dipegang HOD).
- Pengambil ("Saya ambil", `room_issues.claimed_by`/`claimed_at`): satu orang per kendala. Tombol dengan konfirmasi di halaman detail (`RoomIssueController::claim`, pembaruan atomik `whereNull('claimed_by')` supaya dua orang yang menekan bersamaan tidak sama-sama berhasil); status jadi Dikerjakan, tercatat di garis waktu (`kind` ambil). ## Checklist (alur pengisian, simpan otomatis)
- Satu checklist = satu staff + satu jabatan + satu tanggal (unik `employee_id, position_id, date`). Disalin saat dibuat (departemen, nama jabatan, judul & standar tugas) sehingga riwayat utuh saat pegawai pindah /
  keluar atau tugas diubah. Dibuat saat "Mulai checklist" (`FillController::start`, `ChecklistService::start`: semua tugas belum diisi; memulai kombinasi yang sama membuka yang lama).
- Halaman `/isi` (`FillController::create`) untuk HOD / HR / Admin = PAPAN TIM: tanggal (panah hari sebelumnya / berikutnya, tidak ke depan) + departemen (bila lebih dari satu), angka ringkas yang juga menyaring daftar (Semua / Perlu diisi / Lengkap / Direview), kotak "Buat checklist hari ini" untuk departemen + tanggal itu ("Semua departemen" bila lebih dari satu), lalu daftar setiap staff aktif (dari data Absensi; dirinya sendiri disembunyikan kecuali Admin / HR atau sudah punya checklist) dengan status Belum dibuat / Belum diisi / Belum lengkap / Lengkap / Sudah direview / Jadwal belum diisi (staff tanpa jadwal di Absensi untuk tanggal itu: baris dibuat pudar, tombol Mulai dinonaktifkan, tidak dihitung sebagai perlu dibuat; kalau jadwal Absensi tidak terbaca, tidak ada yang ditandai dan pesannya ditampilkan), progres, dan satu tombol (Mulai dengan jabatan checklist staff itu / Isi / Lanjutkan / Lihat / Atur jabatan), pencarian nama bila lebih dari 6 staff. Jarang dipakai dilipat: "Checklist dengan jabatan lain" (pilih staff + jabatan manual) dan "Pengaturan tim" (Atur jabatan staff, Atur tugas tim, jam pembuatan otomatis).
  "Dicek oleh" TIDAK diisi manual: otomatis nama akun yang memulai checklist (HOD / HR / Admin; null = "Diisi sendiri" untuk staff), tidak bisa diubah lewat simpan otomatis. Staff berakun TIDAK punya form mulai di halaman ini: hanya panel "Lanjutkan checklist" (checklist miliknya yang belum lengkap, dibuat HOD/HR/Admin); Riwayat (`/checklists`) miliknya sendiri lewat menu header (`ChecklistController::index`, staff hanya `employee_id` sendiri). `/checklist` mengalihkan ke sini. Panel "Lanjutkan checklist" = yang belum lengkap (7 hari), untuk HOD / HR / Admin tanpa yang sudah tampil di papan tim.
- Halaman kerja `/checklists/{id}/isi` (`ChecklistController::fill`, view `checklists/work`): TIAP PILIHAN TERSIMPAN OTOMATIS, tidak ada tombol simpan. Tampilan Kartu = SATU TUGAS PER LAYAR (dek `[data-deck]` dengan CSS scroll-snap horizontal; sections dan `.cl-body` dibuat
  `display: contents` supaya semua kartu jadi anak langsung dek): geser jari kiri/kanan, panah, papan ketik, segmen progres per tugas (berwarna sesuai status, bisa diketuk), "Lihat semua tugas" (kotak nomor untuk loncat),
  setelah Done kartu berikutnya terbuka SENDIRI (selalu, tanpa pilihan; Ongoing/Pending tidak pindah), dibuka di tugas pertama yang belum diisi, slide terakhir = Ringkasan (tugas tambahan + catatan umum),
  tombol status bertumpuk besar, di layar lebar satu kartu di tengah (maks 40rem). Tombol Kartu / Daftar / "Lihat semua tugas" berupa IKON: "Lihat semua tugas" di kiri, Kartu / Daftar di kanan atas. Tampilan Daftar = baris rapat yang tetap bisa diisi. Pilihan tampilan diingat di perangkat (localStorage); satu markup, gaya dipilih `data-view` di
  `resources/css/app.css` (`.cl-*`). Catatan otomatis untuk Ongoing/Pending, "Cara / standar",
  tanpa tombol "Kosongkan" dan "Sisa tugas = Done" (sengaja dihapus; menekan lagi pilihan yang sedang terpilih membatalkannya, status kembali kosong), progres + skor sementara + "Lengkap ✓" + tombol "Selesai · lihat hasil" yang DISEMBUNYIKAN sampai skor sementara 100% (semua tugas Done; "Lihat hasil" di atas halaman tetap selalu ada), tugas tambahan (tidak dihitung skor), catatan umum. Indikator simpan + "Coba simpan lagi" + peringatan saat menutup halaman.
- API simpan otomatis (JSON, semua lewat `Gate update`): `PATCH checklists/{c}/items/{item}` (status boleh null; Pending tanpa alasan tetap tersimpan), `POST clear`, `PATCH checklists/{c}` (note,
  extras; hanya kunci yang dikirim). `resources/js/checklist.js`: antrean per kunci, ketikan ditunda 700 ms dan dikirim saat berpindah isian, keadaan terbaru dibaca dari layar. Sesi habis -> 401 JSON (`EnsureActiveSession`).
- Lengkap (`Checklist::isComplete`, turunan, bukan kolom): semua tugas berstatus dan setiap Pending beralasan (`CHECKLIST_PENDING_NOTE_REQUIRED`). Checklist boleh tersimpan setengah jadi ("Belum lengkap n/m" di daftar & detail),
  tetapi hanya yang lengkap yang bisa direview. `checklist:prune-empty` (harian 03:00) menghapus checklist tanpa satu pun isian yang lebih tua dari 2 hari.
- Buat checklist sekaligus (`BulkAssignController`, `BulkAssignService`, tombol "Buat checklist hari ini" di `/isi`): membuatkan checklist KOSONG untuk setiap staff yang masuk kerja pada tanggal itu (boleh mundur, tidak ke depan),
  menurut jadwal Absensi (`AttendanceApiService::schedules`, endpoint Absensi `GET /api/v1/tasks/schedules?date=`: work / off / leave+kode / unscheduled). Dilewati: libur (OFF), izin/cuti/sakit/PH, jadwal yang BELUM DIISI (tidak dibuatkan, keputusan pengguna),
  dan staff yang jabatan checklistnya belum diatur (dilaporkan dengan nama). Aman ditekan berulang (yang sudah ada dihitung "sudah ada"). HOD hanya departemennya, HR/Admin semua; GM dan staff ditolak. Ringkasan tampil di halaman.
  Checklist yang dibuatkan ditandai `assigned_at`, `checked_by` kosong sampai atasan (bukan stafnya) pertama mengisinya (`ChecklistService::touch`), dan TIDAK dibersihkan `checklist:prune-empty` walau kosong ("Belum diisi", dasar dashboard "belum dicek").
  Panel "Lanjutkan checklist": HOD/HR/Admin melihat yang belum lengkap di departemen yang boleh diakses (7 hari), staff miliknya.
- Jabatan checklist per pegawai (`/tim/jabatan`, `TeamPositionController`, `employees.checklist_position_id`): diatur sekali oleh HOD (HR/Admin semua; tidak untuk dirinya sendiri kecuali Admin / HR), dengan saran dari teks jabatan Absensi
  (`PositionSuggester`: cocok persis / singkatan di dalam kurung / tepat satu yang memuat; tetap harus disimpan). Staff berakun memakai jabatan ini saat membuka checklist miliknya. Ini SATU-SATUNYA tempat mengatur jabatan: kolom "Jabatan checklist" di Akses pengguna dinonaktifkan (hanya menampilkan, menaut ke Tim → Jabatan) dan tidak pernah disimpan dari sana; `users.position_id` tinggal cadangan lama (migrasi 2026_11_13 memindahkan isinya ke `employees.checklist_position_id` bila kosong). `checklist:cocokkan-jabatan` mengisi jabatan pegawai dari teks jabatan Absensi (simulasi dulu, `--terapkan`).
  Perubahan jabatan di Absensi TIDAK mengubah daftar tugas otomatis. `employees.checklist_title` = teks jabatan Absensi saat jabatan checklist terakhir dikonfirmasi (diisi `TeamPositionController::update` dan `checklist:cocokkan-jabatan`); `Employee::positionReview()` menandai "perlu dicek" bila teks Absensi sekarang berbeda, atau jabatan checklist bukan dari departemen pegawai (pindah departemen). Halaman Tim → Jabatan menampilkan spanduk + baris berlatar kuning + saran jabatan baru (terpilih, belum disimpan) + kotak "Jabatan checklist tetap benar"; menyimpan formulir saja tidak menghapus tanda.
- Parameter isian tugas (`task_parameters`, `checklist_item_parameters`, `parameter_templates`; `App\Checklists\ParameterRules`, `App\Tasks\TaskParameters`): satu tugas bisa punya banyak parameter: status (Done / Ongoing / Pending), angka, stand meter, pilihan (nilai normal), centang, atau teks. Status tugas dihitung dari semua parameter (ada Pending = Pending; ada Ongoing = Ongoing; semua terisi dan normal = Done). Parameter disalin ke item saat checklist dibuat. Setiap jenis yang disimpan masuk ke template (`parameter_templates`) dan bisa dipilih lagi. Editor: `team/partials/parameter-editor`. API item menerima `parameters` (id => nilai).
- Atur tugas hari ini (`/checklists/{c}/tugas`, `ChecklistTaskController`, `ChecklistService::setTasks`, HOD / HR / Administrator, bukan Staff): tugas default pegawai (Atur tugas) dicentang / dihapus untuk checklist hari itu. Tugas yang belum diisi bisa dihapus dan dipilih lagi (disalin dengan parameternya); yang sudah ada isian (status, catatan, nilai, foto) tetap. Perubahan dicatat di log.
- Dua menu terpisah (HOD / HR / Administrator): **Checklist** (`/checklist/atur`, `FillController::assign`) = atur tugas karyawan hari itu: buat checklist (per staff atau sekaligus), atur tugas hari ini; tanpa isian. **Isi checklist** (`/isi`, `FillController::create`) = papan isi checklist harian yang sudah dibuat (Isi / Lanjutkan / Lihat). Staff hanya melihat Checklist saya.
- Hari yang akan datang: Atur tugas (Checklist) boleh sampai 60 hari ke depan (`ChecklistSettings::MAX_DAYS_AHEAD`, policy `plan`). Isi checklist hari berikutnya hanya kalau Administrator mengaktifkan `checklist_future_fill` di Pengaturan > Aturan checklist (policy `update`). Staff melihat rencana tugas hari berikutnya sebagai catatan.
- Hapus rencana masa depan (`PlanController`, route `checklists.plan.destroy` dan `fill.plan.destroy-day`): hanya checklist yang tanggalnya di masa depan, belum ada isiannya (`ChecklistService::hasAnswers`), dan boleh di-`plan` oleh pengguna. Per pegawai atau sekaligus per departemen di papan Atur checklist harian. Dicatat di log.
- Mulai di tanggal selain hari ini (papan Atur checklist harian): popup berisi tugas bawaan pegawai dengan pilihan jabatan lain di departemen yang sama; `POST /checklist/atur/mulai` (`PlanController::start`) membuat checklist dengan jabatan dan tugas yang dicentang (`ChecklistService::start`, parameter `$taskIds`).
- Tugas checklist boleh dari jabatan lain di departemen yang sama (`ChecklistService::departmentTasks`): di popup Mulai dan Atur tugas hari ini, bagian "Tugas dari jabatan lain" (dilipat per jabatan). Tugas departemen lain tidak bisa dipilih.
- Pembuatan otomatis: jam (WITA) per departemen di `departments.auto_assign_at`, diatur HOD (departemennya) / HR / Admin di menu Pengaturan (`/admin/pengaturan`, bagian "Pembuatan otomatis tiap hari"; menu tampil untuk yang boleh mengatur tim); kosong = mati. `checklist:auto-assign` (tiap 5 menit lewat scheduler) membuatkan
  untuk departemen yang jamnya sudah lewat dan belum jalan hari ini (`auto_assigned_on`); gagal membaca jadwal = dicoba lagi 5 menit kemudian, tidak ditandai selesai. Pembuatnya `filled_by` null.
- Foto bukti per tugas (`checklist_item_photos`, `ChecklistPhotoService`, `ChecklistPhotoController`): di tiap kartu tiga tombol aksi sejajar dan sama lebar (`.cl-actions`: Kamera, Galeri, Catatan; yang tidak relevan disembunyikan, sisanya melebar), lalu foto kecil (`.cl-thumbs`) dan kolom catatan di bawahnya. Tombol: "Kamera" (dialog kamera di halaman: `getUserMedia`, pratinjau langsung, tombol potret, "Balik kamera" depan/belakang, tetap terbuka sampai batas foto; butuh HTTPS atau localhost,
  bila tidak tersedia / izin ditolak jatuh ke kamera bawaan HP lewat `<input capture=environment data-photo-native>`) dan "Galeri" (`<input type=file accept=image/* multiple>` tanpa `capture`), maksimal 3 foto per tugas
  (`config/checklist.php` -> `photos.per_task`). Dikecilkan di HP dulu (`compress()` di `checklist.js`: sisi terpanjang 1280 px, JPEG 0.8), lalu server mengolah ulang dengan GD (putar sesuai EXIF, maks 1600 px, JPEG baru tanpa metadata;
  file yang bukan gambar ditolak). Disimpan di disk privat `local` (`storage/app/private/checklist-photos/{checklist}/{uuid}.jpg`), TIDAK di folder publik: hanya dilayani `GET /checklists/{c}/photos/{photo}` setelah `Gate view`.
  Tambah / hapus lewat `Gate update` (terkunci setelah direview, kecuali HR/Admin). Menghapus checklist ikut menghapus berkasnya. Foto ikut tampil di detail dan hasil cetak.
- Kesehatan sistem (bagian "Kesehatan sistem" di `/admin/pengaturan`, `App\Health\SystemHealth`, hanya Administrator): jadwal (denyut `schedule:run` tiap menit lewat Cache `scheduler.heartbeat`; pembuatan otomatis; sinkron Absensi; hapus foto lama dari Cache `photos.last_prune`), penyimpanan (disk, foto, database), aplikasi (mode, HTTPS, migrasi, error 24 jam dari laravel.log, koneksi Absensi, TLS), dan server (PHP, batas unggah, ekstensi, OPcache). Tidak memanggil API Absensi.
- Pengaturan Administrator (`/admin/pengaturan`, `Admin\SettingsController`, tabel `settings`, `ChecklistSettings` scoped): `photo_requirement` = optional / pending (wajib untuk tugas Pending) / all (wajib untuk semua tugas) dan
  `photo_retention_days` (bawaan 90, 0 = tidak pernah). Foto wajib yang belum ada membuat checklist "belum lengkap" (`Checklist::missingPhotos`, ikut `isComplete`), jadi belum bisa direview. `checklist:prune-photos` (harian 03:30)
  menghapus foto yang lewat masa simpan; isian checklist tetap ada. Server produksi: `upload_max_filesize` >= 8M dan `post_max_size` >= 10M (HP sudah mengecilkan foto, tapi server menerima sampai 8 MB).
- Status: `saved` (Belum direview) → `hod_reviewed` (Direview oleh HOD; terkunci untuk HOD dan staff, HOD bisa "Batalkan review" untuk mengedit lagi) → `reviewed` (Direview oleh GM/HR; terkunci, hanya HR/Admin bisa mengubah). HOD menekan "Tandai sudah direview" untuk checklist departemennya dan miliknya sendiri; GM/HR/Admin menekan "Tandai sudah direview" untuk checklist orang lain, juga dari status Direview oleh HOD (tercatat siapa & kapan, bukan checklist sendiri); sesudahnya HOD/staff tidak bisa mengubah,
  HR/Admin masih bisa edit dan hapus. Detail `/checklists/{id}` (ringkasan, skor n/N Done, pil, tugas tambahan, Edit, Cetak, Hapus). Tombol Cetak tidak ditampilkan untuk peran Staff. Daftar `/checklists` (menu Riwayat) per rentang tanggal (`from`/`to`, bawaan hari ini; kolom Tanggal; filter departemen & status berlaku langsung, tanpa tombol Tampilkan).
- Skor = persentase tugas Done; warna: >= 90 hijau, 70-89 emas, < 70 merah.
